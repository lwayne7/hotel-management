# 易宿酒店预订平台答辩高频问答

## 1. 你们如何保证“实时更新价格”？
**答：**
- H5 端通过 SSE 订阅 `/api/public/hotels/price-updates`。
- 事件采用统一结构：`type`、`timestamp`、`hotelId?`、`changeKind`、`version?`。
- 前端收到事件后优先做“按 hotelId 增量刷新”，仅在必要场景（例如酒店上线）触发全量刷新。
- 小程序/RN 使用轮询兜底，保证多端稳定性。

## 2. 为什么不是所有端都用 SSE？
**答：**
- 端能力与网络环境差异较大，H5 对 SSE 原生支持最好。
- 小程序/RN 采用轮询兜底是稳定性优先的工程取舍，降低端兼容风险。
- 这不是功能缺失，而是分层实现策略。

## 3. 定位功能精度如何？
**答：**
- 当前是城市级定位：用于城市筛选和城市中心地图落点。
- 未宣称公里级距离排序，已在 README 和答辩边界中明确说明。
- 若继续迭代，可接入逆地理服务与距离计算。

## 4. 下线和删除有什么区别？
**答：**
- 删除仅限草稿，属于数据移除。
- 下线是状态变更（`approved -> offline`），可随时恢复上线（`offline -> approved`）。
- 用户端公开接口只返回已发布酒店，因此下线后用户端不可见。

## 5. 商户是否可以编辑已发布酒店？
**答：**
- 可以编辑，但保存后状态自动转待审核（`approved/offline -> pending`）。
- 这样保证线上酒店变更必须经过管理员复核。

## 6. 如何证明长列表性能做了优化？
**答：**
- 列表页采用分页 + 虚拟滚动（超过阈值开启）。
- 只渲染可见区和缓冲区元素，显著降低长列表渲染开销。
- 演示时可通过“已启用虚拟滚动”提示和流畅滚动体验展示。

## 7. 权限是如何做的？
**答：**
- 后端采用 JWT + RolesGuard，接口按角色严格授权。
- 前端路由层有 `AuthRoute` 做角色守卫。
- 登录后按用户角色自动跳转到商户或管理员视图。

## 8. 驳回原因如何回传给商户？
**答：**
- 管理员驳回时必须填写原因。
- 原因保存到酒店记录，商户列表可直接查看，管理员列表也可快捷查看。

## 9. 如何保证代码质量？
**答：**
- 管理端前端已通过 lint 和构建。
- 后端已通过构建和测试。
- 移动端已通过 typecheck 和单测。
- 同时补齐了需求-实现矩阵、演示脚本和自评表，降低答辩口径风险。

## 10. 为什么不实现支付下单？
**答：**
- 本项目严格按题目范围实现“酒店查询/列表/详情 + 管理审核发布流程”。
- 下单支付属于扩展能力，不在本次评分主线中，后续可作为迭代项。
